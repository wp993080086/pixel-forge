## 一、总体判断

### 做得好的部分（先肯定，避免过度否定）

1. **定位清晰**：纯本地、不上传、多端差异化，一句话能说清，边界守得住。
2. **附录机制有效**：13 个待定项逐条拍板并回写正文，标注「附录 #N 已拍板」，可追溯性强。这在需求文档里算优秀实践。
3. **像素级严谨度罕见**：二.3 把「原图像素 vs 屏幕像素」的换算举例写清楚、二.4 强制整数像素吸附、二.5 禁止选区漂移——这三条是同类工具最常见的 bug 源，写进 PRD 说明作者踩过坑。
4. **风险意识**：附录 #13 主动质疑 `image` 包编码能力，方向完全正确（只是结论需要修正，见下）。

### 核心问题一句话

**PRD 把「技术上做不到」的三件事写成了「已支持」（WebP 导出、SVG 光栅化、移动端系统保存面板），把「需要架构决策」的一件事写成了「已拍板」（内存模型），而这些都会在开发中期才暴露，届时返工成本最高。**

## 二、技术硬伤（实测证据，必须修）

### 🔴 硬伤 1：导出 WebP 在当前技术栈下不可实现

**PRD 怎么说**：一.导出列 WebP；四.2「PNG→WebP 保留透明」；四.5「WebP 支持透明，转换时保留 Alpha」；五.3「WebP 压缩支持有损/无损」；九.4「WebP 质量默认 80」。

**实测结果**：

```
image-4.12.0/lib/src/formats/
├── webp_decoder.dart        ← 只有解码
├── webp/                    ← 只有 vp8 解码相关 14 个文件
│   （vp8.dart / vp8l.dart / webp_alpha.dart / webp_frame.dart ...）
└── ❌ 无 webp_encoder.dart
```

全库检索 `WebPEncoder` 类：**0 处命中**。`image` 包从 4.x 起从未提供 WebP 编码器，这是长期已知限制，不是版本问题。

**影响面**：
- 四.格式转换中 WebP 作为目标格式的三条承诺全部落空
- 五.3「WebP 压缩」整节失效
- 九.4「WebP 质量 1–100」参数无意义
- 十一.1 验收标准「PNG→WebP 后 alpha 逐像素一致」——**验收条款本身不可执行**
- 十章兼容表把 WebP 导出标为 ⚠️「待调研」，但正文（四/五）已经把它写成已支持，**文档内部自相矛盾**

**可选方案（需拍板）**：

| 方案 | 成本 | 风险 |
|------|------|------|
| A. MVP 砍掉 WebP 导出，只保留 WebP 导入（解码→转 PNG 导出） | 极低 | 产品承诺缩水，但诚实 |
| B. 引入 FFI（libwebp） | 中高 | 直接破「纯 Dart 铁律」，Windows/Android/鸿蒙三端各要编 native 库，鸿蒙风险极大 |
| C. 自研纯 Dart WebP 编码器（VP8L 无损优先，有损几乎不可能） | 极高 | 半年起步，不建议 |

**建议**：选 A。同时修正一/四/五/九/十/十一 六处相关表述，把 WebP 从「导出格式」降级为「导入格式」。

> 附带说明：附录 #13 把 WebP 和 ICO 混在一条里问「image 4.x 疑似仅支持解码、不支持编码」，但实际情况是**WebP 不能编码、ICO 能编码**，两个结论相反。这条附录需要拆成两条独立结论。

### 🔴 硬伤 2：SVG 导入无法遵守「纯 Dart 铁律」

**PRD 怎么说**：一.导入列 SVG；一.边界 1「仅渲染为位图导出，光栅化尺寸在导入时选择」；十章给 Windows/鸿蒙/Android/Web 全打 ✅。

**实测结果**：`image` 包 `formats/` 下**无任何 SVG 解码器**（确认无 svg 相关文件）。纯 Dart 生态也基本没有可用于生产的光栅化器。

**唯一可行路径**：`flutter_svg`（把 SVG 渲染成 `ui.Picture`）→ `PictureRecorder` → `Image.toByteData()` 取像素。**这条路全程依赖 Flutter Engine（Skia/Impeller），是彻底的平台能力，不是 Dart 能力。**

**影响**：
1. 直接违反七.2「图像编解码全部走纯 Dart 库」的架构铁律——PRD 需要明确写「SVG 光栅化是铁律的唯一例外」。
2. Web 端风险高：`flutter_svg` 在 CanvasKit 下可用，但 HTML renderer 下表现差异大；若最终切 wasm，还需额外验证。
3. **单元测试无法覆盖**：`flutter test` 无 GPU 上下文时 `toImage()` 行为不稳定，SVG 光栅化只能靠集成测试/golden 测试。
4. 二.3 的「钳制上限 = 原图对应边尺寸」对 SVG 语义不成立——**SVG 的「原图尺寸」是什么？** 光栅化选 512 后再裁剪，上限是 512 还是 viewBox？PRD 没答。

**建议**：
- 在七.2 补一条明确例外：「SVG 光栅化允许依赖 Flutter Engine，其余链路仍为纯 Dart」
- 把 SVG 从 MVP 的 ✅ 降为「Windows 先行，Android/鸿蒙跟随，Web 待定」
- 明确 SVG 的「原图」= 导入时光栅化所得的位图，裁剪上限以光栅化后尺寸为准

### 🔴 硬伤 3：Android / 鸿蒙「唤起系统保存面板」这个抽象不存在

**PRD 怎么说**：六.2「导出：保存到设备本地，**唤起系统保存面板**」；七.3 鸿蒙/Android 标「系统保存面板」。

**实测结果**：`file_selector_android` 在 `pubspec.lock` 中已锁定，但**未实现 `getSaveLocation`**（该平台实现只有 `openFile` / `openFiles`；全缓存目录检索 `getSaveLocation` 仅 `file_selector_windows` 命中）。

**原因**：Android 根本没有「系统级保存对话框」这个概念。等价能力是 SAF 的 `ACTION_CREATE_DOCUMENT`（需另外的插件，如 `flutter_file_dialog`），或者写 MediaStore（需权限）。鸿蒙同理，`PhotoViewPicker` 的保存语义是「存入媒体库」而非「选择路径」。

**影响**：
- 六.2 的写法在移动端实现不了，会导致开发时才发现要换插件
- 而七.2 要求「插件引入前逐个核对 ohos 适配清单」——**这个插件选型必须在 PRD 阶段就定下来**，否则鸿蒙适配面失控
- `file_selector` 是官方多端插件、鸿蒙适配较好；一旦换成社区插件（`flutter_file_dialog` / `share_plus`），鸿蒙适配风险陡增

**建议**：把六.2 改成显式的**分端导出通道矩阵**：

| 端 | 导入 | 导出 |
|----|------|------|
| Windows | `file_selector.openFile` + 拖拽 | `file_selector.getSaveLocation` → 写文件 |
| Android | `file_selector.openFile`（13+ Photo Picker） | 方案待定：① `flutter_file_dialog` SAF ② MediaStore ③ 先写临时目录再 `share_plus` 分享 |
| 鸿蒙 | 对应 `file_selector_ohos` | 同上，需核对 ohos 变体包 |
| Web | `<input type=file>` / paste | Blob + `<a download>` |
| 小程序 | `wx.chooseMedia` | `wx.saveImageToPhotosAlbum` |

这张表不定，移动端导出就是个空头承诺。

### 🟠 硬伤 4：内存模型自相矛盾，100MP 上限对移动端不现实

**PRD 九.3 原文**：
> 预览降采样：原图边长 > 4096px 或总像素 > 2000 万时，解码后降采样至长边 ≤ 2048 用于编辑预览；**导出/处理时使用全分辨率数据**
> 处理上限：总像素 > 10000 万（100MP）直接拒绝

**两个问题**：

**(1) 逻辑矛盾：既要降采样省内存，又要保留全分辨率**

如果解码后保留全分辨率位图，降采样就只多了一份内存、一点没省。如果丢掉全分辨率，导出时必须**重新解码一次原文件**。PRD 完全没提这个二次解码，也没提它带来的：
- 导出耗时翻倍（100MP PNG 解码在移动端 3–8 秒）
- 两次解码之间的编辑参数必须能重放（当前「独立单任务」模型下勉强可行，但未写明）
- peak memory = 预览图 + 全尺寸图 + 编码输出缓冲，**同时存在**

正确写法应该是：
> 解码全图 → 生成 ≤2048 预览图 → **立即释放全图** → 编辑基于预览图 + 变换参数（选区/尺寸用原图坐标系记录）→ 导出时从原文件重新解码全图 → 应用参数 → 编码 → 释放

这实际上把架构从「编辑位图」推向「编辑参数 + 延迟渲染」。**这是个必须先拍板的架构决策，不是实现细节。**

**(2) 100MP 上限算错了移动端内存**

| 环节 | 内存占用（100MP RGBA8） |
|------|------------------------|
| 解码后原图 | 100M × 4B = **400 MB** |
| 缩放/裁剪输出副本 | 再 400 MB（大图 upscale 更甚） |
| 编码输出缓冲 | 数十 MB |
| **峰值** | **≈ 850 MB+** |

Android 中低端机 heap 上限普遍 256–512 MB，鸿蒙同档。**100MP 在移动端 100% OOM**，而且 Dart 的 OOM 是进程级 crash，catch 不住，PRD 九.2 的「错误卡片」兜不住。

**建议改为按端内存预算**：

| 端 | 处理上限 | 依据 |
|----|---------|------|
| Windows | 100 MP | 桌面内存充足 |
| Android / 鸿蒙 | **24–32 MP**（约 128 MB 位图） | 中端机 heap 512 MB，留 3× 余量 |
| Web | 桌面 50 MP / 移动浏览器 **8–16 MP** | Safari canvas 面积限制比 Chrome 严得多 |

Web 的 5000 万（PRD 现值）在 iOS Safari 上同样会失败——`九.3` 的分端差异化完全缺失。

### 🟠 硬伤 5：所有编解码必须在 Isolate 中执行（PRD 未提）

PRD 八.4 只写了「裁剪、转换、压缩过程展示加载进度」，没写**在哪执行**。

在 Flutter 主 isolate 里跑 400MP 级解码，UI 直接冻结数秒，进度条都动不了（进度条本身也卡死）。**必须明确**：

- Windows / Android / 鸿蒙：`Isolate.run()` 或 `compute()`，解码/缩放/编码全在后台 isolate，主 isolate 只收进度回调
- **Web 是例外且是坑**：Flutter Web 的 `compute()` 是**同步执行**的，没有真线程。50MP 解码 = 页面假死。Web 端要么降上限、要么用 Web Worker（需要自定义 glue code，成本高）
- Isolate 之间传大图要用 `TransferableTypedData`，否则会拷贝一份（内存翻倍）

这条不写进 PRD，等于把最大的性能坑留给开发自己发现。

### 🟡 硬伤 6：元数据剥离过度——会把色彩和 DPI 一起弄坏

**PRD 八.6**：
> 导出默认剥离全部元数据（零 EXIF），定位为隐私特性

「全部」是个危险的词。图片元数据至少分两类：

| 类别 | 例子 | 该不该剥 |
|------|------|---------|
| **隐私类** | EXIF（GPS、拍摄时间、设备型号、序列号）、XMP | ✅ 必须剥，PRD 立场正确 |
| **渲染类** | ICC Profile（色彩空间）、pHYs（DPI）、gAMA、sRGB chunk、iCCP | ❌ **剥了会出问题** |

**具体后果**：

1. **广色域照片偏色**：iPhone 的 Display P3 照片带 ICC profile。剥离后，像素值仍是 P3 数值，但没有任何标记说明它是 P3，看图软件按 sRGB 解释 → **颜色明显发灰/发暗**。这是用户能直接看出来的质量问题。
2. **打印尺寸错乱**：300 DPI 的 PNG 剥离 pHYs 后，打印默认为 72 DPI，A4 图变成 4 倍大。
3. **跟八.8 自相矛盾**：八.8 专门讨论「色彩管理」（CMYK JPEG、16-bit PNG 降级），说明作者意识到色彩有问题；但八.6 一句话把 ICC 剥了，八.8 的努力白费。

**巧的是，库本身完全支持保留**：`png_encoder.dart` 里有 `_writeICCPChunk()`（写 iCCP），构造参数还有 `pixelDimensions`（写 pHYs）。**技术上零成本，纯粹是需求写错了。**

**建议改为**：
> 导出剥离**隐私类**元数据（EXIF / GPS / XMP / 设备信息），保留**渲染类**元数据（ICC Profile / pHYs / gAMA）。若源图色彩空间非 sRGB 且目标格式支持 ICC，则写入转换后的 sRGB profile；不支持 ICC 的目标格式（BMP）在导入后即做 P3→sRGB 转换。

### 🟡 硬伤 7：APNG 与 PNG 共用 `.png` 扩展名 → 会静默丢帧

**PRD 一章**把 APNG 与 PNG 并列为两种格式，但两者扩展名完全相同（都是 `.png`），只能靠文件头 `acTL` chunk 区分。

**现有代码已经踩了这个坑**：

```dart
// lib/core/image/image_format.dart:39-51
ImageFormat.png  => ['png'],
ImageFormat.apng => ['png'],   // ← 同一个扩展名

static ImageFormat? fromExtension(String ext) {
  for (final f in ImageFormat.values) {   // png 枚举在前
    if (f.extensions.contains(e)) return f;   // 'png' 永远返回 png
  }
}
// → ImageFormat.apng 永远不可达
```

后果：用户导入一张 APNG，被当作静态 PNG，**所有帧除第一帧外静默丢弃**，且没有任何提示。

**PRD 缺的是「格式探测规则」**：
- 必须按 **magic bytes** 探测，不能靠扩展名：PNG `89 50 4E 47`、JPEG `FF D8 FF`、GIF `47 49 46 38`、WebP `52 49 46 46 xx xx xx xx 57 45 42 50`、BMP `42 4D`、ICO `00 00 01 00`
- PNG 内部再查 `acTL` 判断 APNG
- 需列出**扩展名与真实内容不一致**时的策略（如 `.jpg` 实为 PNG）：按内容处理 + toast 提示，还是直接拒绝？
- WebP 再查 `VP8X` + `ANIM` 标志判断是否动图 WebP

### 🟡 硬伤 8：动图相关逻辑有 4 处未定义

一章边界 2 定的是「动图仅预览，裁剪后导出静态位图」。但没定义：

1. **导出哪一帧？** 第一帧？预览时用户停留的那一帧？必须给一个规则（建议：默认第一帧，若用户手动翻帧则取当前帧）。
2. **多帧内存上限？** 九.3 只讲了单张像素上限，没讲帧数。一个 200 帧的 800×800 GIF = 200 × 2.56 MB = **512 MB**。必须有硬上限（建议 ≤50 帧或总解码像素 ≤ 2 亿）。
3. **`webp_frame.dart` 存在说明 image 包能解动图 WebP**，但一动图 WebP 导出不了（见硬伤 1），二一动图 WebP 的「同 GIF/APNG 处理」表述要相应修正。
4. **动图预览降采样**：九.3 的降采样对动图是「每帧都降」还是「只解第一帧」？后者省内存但没法预览动画。

### 🟡 硬伤 9：ICO 导出可行，但 3 个约束没写进 PRD

**实测：ICO 编码可用**。

```
ico_encoder.dart → WinEncoder.encodeImages()
  内嵌 PngEncoder().encode(img)  ← PNG-in-ICO（Vista+ 支持）
  硬限制：if (img.width > 256 || img.height > 256) throw
```

所以附录 #2 定的「默认勾选 16/32/48/64/128/256 全套打包」**技术上可实现**，但 PRD 漏了：

1. **原图小于目标图标尺寸怎么办？** 16×16 原图生成 256×256 图标要 upscale 16 倍，质量惨不忍睹。需规则：`目标尺寸 > 原图尺寸` 的项自动取消勾选并置灰。
2. **ICO 内部缩放用哪种重采样算法？** PRD 三.3 让用户选算法，但 ICO 多尺寸导出时是一次选算法套用到全部尺寸，还是各尺寸自动选（小图适合 nearest/area，大图适合 lanczos）？**逐尺寸自动选更合理，PRD 未提。**
3. **九.4 的导出命名规则 `{原名}_{1200x800}.{ext}` 对 ICO 不成立**（多尺寸没有单一宽高），需要单独规则如 `{原名}_icon.ico`。

> 顺带：`ico_encoder` 明确要求 ≤256，PRD 默认值刚好卡在上限，**没有余量**。若未来想加 512 图标，库层面直接抛异常。

### 🟡 硬伤 10：圆形选区的抗锯齿与「alpha 逐像素一致」验收冲突

**二.7** 说圆形选区「圆形区域保留图像，圆外填充透明」。但圆形边缘在像素网格上必然有半透明过渡（抗锯齿），否则锯齿严重到不可用。

而 **十一.1** 的验收标准是「半透明 PNG 经裁剪后 **alpha 值逐像素一致**」。

**这两条无法同时满足**：圆形裁剪必然改变边缘像素 alpha。验收标准需要拆开：
- 矩形/自由选区裁剪 → alpha 逐像素一致（严格）
- 圆形选区 → 圆心区域 alpha 一致，边缘 1px 过渡带允许变化

同时 PRD 需要明确：圆形边缘**要不要**抗锯齿（建议要，否则成品不可用），以及导出尺寸（二.3 说输出方形画布，边长 = 选区宽 or 高？圆形是正方形内切，取短边？）。

### 🟢 硬伤 11：BMP 透明能力需要在 PRD 内部统一说法

**九.4**「透明底：仅 PNG/WebP/BMP 导出时可用」
**八.2**「凡是目标格式支持 Alpha 通道的，必须保证不丢失透明」
**现有代码** `image_format.dart:54` → `ImageFormat.bmp => false`（认为 BMP 不支持 alpha）

**实测**：`bmp_encoder.dart:44` 注释写着 `only 32bpp supports alpha`，即 32bpp + BITMAPV5 头 + bitfields 时机制上能写 alpha。

**但生态现实是**：Windows 图片查看器、多数浏览器、微信都**忽略** BMP 的 alpha 通道，透明区域显示为黑色或白色。所以「BMP 支持透明」是**技术可写、生态不可靠**。

**建议**：把 BMP 从九.4 的「透明底可用」列表移除，并在四章加一句提示；`image_format.dart` 的 `false` 判���是正确取舍，PRD 应向代码对齐。

## 三、逻辑不自洽（产品层，不影响实现但影响体验）

### 3.1 「独立单任务」模型与「转换+压缩」是一体的，硬拆了体验很差

九.1 定的是「裁剪/尺寸/转换/压缩 四个独立单任务，不支持跨功能串联」。

但**格式转换和压缩在物理上是同一个动作**：

- 转 JPG：必须给质量参数（否则用什么？）
- 转 WebP：必须有损/无损 + 质量
- 压缩 JPG：必然输出 JPG，本质就是「重新编码」
- 压缩 PNG 有损调色板：本质是「改变色深后重新编码」

用户的实际诉求是「把这图转成 WebP、体积压到 200KB 以内」——**一个动作，PRD 要求走两个页面，中间还多一次有损重编码**（PNG→WebP 一次，WebP 再压一次，二次损失）。

**建议**：把「格式转换」和「压缩」合并为统一的**导出面板**（格式 + 质量/压缩模式 + 预估体积同屏），保留「裁剪」「尺寸变换」为独立编辑任务。这样既符合用户心智，也去掉一次无谓的有损叠加。

### 3.2 裁剪「指定目标像素尺寸」缺少定位规则

二.3 说输入 1200×1200 → 在原图上框选对应区域。但**输入尺寸本身就锁定了选区大小，用户只剩平移自由度。初始落在哪没定义**。

必须补：默认居中？保持选区中心不变？左上角对齐？建议「以当前选区中心为锚点，若超出边界则向内钳制」。

### 3.3 正方形选区 / 1:1 预设 / 圆形选区，三者关系混乱

二.2 同时列了「正方形选区」和「1:1 比例预设」——**这两者是同一件事**。而「圆形选区」叠加「16:9 预设」时是什么？椭圆？PRD 没定义。

建议矩阵化：

| 形状 | 自由拖拽 | 1:1 | 4:3 | 3:2 | 16:9 |
|------|---------|-----|-----|-----|------|
| 矩形（含正方形） | ✅ | ✅ | ✅ | ✅ | ✅ |
| 圆形 | 仅正方形（内切） | ✅ | ❌ 置灰 | ❌ | ❌ |

圆形只在 1:1 下有意义，其余比例要么置灰要么自动降为矩形。

### 3.4 「单步撤销」与「重置」语义重叠

八.7 同时提供「重置/重新载入原图」和「单步撤销」。但在独立单任务模型下，一个功能页只做一件事：

- 裁剪页 → 只有选区变化，「撤销」= 恢复上一个选区？还是恢复裁剪动作（但裁剪后就导出了，没得撤）？
- 压缩页 → 只有质量滑块变化，「撤销」= 滑块回上一次值？这毫无意义。

**基本可以判定：单步撤销在 MVP 的实际价值接近于零，而实现成本（快照一份位图）在移动端是灾难**（再存一张 400MB）。

**建议**：MVP 只做「重置」，把「单步撤销」也移入需求池（和六.8 撤销栈合并），省下的内存和工期更值。

### 3.5 「位图格式可互相转换」的表述含混

四.1「任意支持导入的**位图**格式，可单向转换到支持导出的格式」。但导入列表里 SVG（矢量）、ICO（容器）、GIF/APNG（动图）都不是「位图」。按字面理解，这三类被排除在转换之外，但一章又说 SVG 能光栅化导出。

**缺一张明确的 N×M 转换矩阵**，标出每格的：可用 / 需特殊处理（光栅化/取首帧/丢透明/需调色板）/ 不可用。这是开发时最容易被反复问的东西，用表格一次说清能省大量沟通。

### 3.6 压缩功能缺「预估输出体积」——这是压缩工具的核心反馈

五章压缩只给了质量参数，但**用户调压缩参数唯一关心的就是「能从 5MB 压到多少」**。没有体积预估，就是盲调。

**建议**：质量滑块旁显示实时（或 debounce 300ms）预估体积 + 压缩率。实现上可用「降采样后快速编码估算」再按像素数外推，不必全图编码。这条应该进 MVP，而不是需求池。

### 3.7 WebP 源文件导出会静默降级

九.4「导出默认格式与源格式一致，源格式不在导出列表时回退 PNG」。

WebP 一旦确认不能导出（硬伤 1），用户导入 WebP → 导出时格式变成 PNG，**文件体积暴涨数倍，但界面不提示**。必须加提示：「WebP 暂不支持导出，已改为 PNG」。

## 四、文档级冲突（跨文件，需同步修订）

### 4.1 鸿蒙 SDK 版本三方打架

| 出处 | 表述 |
|------|------|
| `AGENTS.md` | 「开发基线：官方 Flutter **3.44.9**」；「代码 API 面控制在 **3.41** 兼容范围内」 |
| PRD 七.2 | 「版本锁定 ohos 稳定线（建议 **3.35.x-ohos** 或 3.41.x-ohos）」 |
| `pubspec.yaml` | `environment: sdk: ^3.12.2` |

**问题**：Dart 3.12 只存在于 Flutter 3.4x 线。若真按 PRD 选 **3.35.x-ohos**，其 Dart 版本约 3.9，**直接违反 `sdk: ^3.12.2`**，`flutter pub get` 就过不去。而且 `flutter_riverpod ^3.4.3`、`go_router ^18.1.2` 也都有更高的 SDK 下限。

**建议**：删掉 3.35 选项，把 PRD 七.2 统一为「**3.41.x-ohos 及以上，与 AGENTS.md 的 3.41 API 面基线对齐**」，并注明「若 ohos 稳定线落后于 3.41，则以 ohos 稳定线为准，同时下调 pubspec 的 SDK 约束」。

### 4.2 现有代码已经跑到 PRD 前面了

`lib/core/platform/capabilities.dart:56` 给 Windows / 鸿蒙 / Android 都配了 `ImageFormat.ico` 导出，而 PRD 十章把 ICO 导出标为 ⚠️「可行性待 #13」。现在实测 ICO 可编码，所以代码是对的、PRD 落后了——**附录 #13 结案后应把这三端的 ICO 从 ⚠️ 改为 ✅**。

但 Web 端 `exportFormats: _mainstreamExport`（不含 ICO），与七.4 的「ICO 导出直接阉割」一致，没问题。

### 4.3 「262 个已适配库」是不可验证的断言

PRD 七.2 写「插件引入前逐个核对官方适配清单（已收录 262 个已适配库）」。数字无来源、无时间戳，半年后必然过期。建议改为「截至 2026-11，OpenHarmony-SIG/flutter_packages 收录约 262 个已适配库（**开发时以清单实时状态为准**）」。

## 六、需求池的补充建议

现有需求池分类合理，补几条**成本低、收益高**的：

1. **按目标体积压缩**（压到 ≤200KB）：比质量滑块更符合真实诉求，压缩类工具的标配。
2. **渐进式 JPEG 开关**：网页场景省流量，`image` 包 `JpegEncoder` 的 `progressive` 参数直接支持，几乎零成本。
3. **色度抽样开关**（4:2:0 / 4:4:4）：JPG 压缩体积差异可达 30%，专业用户刚需。
4. **常用尺寸预设提前**：需求池五.5 已列「头像/小红书/公众号」，但对中文用户价值极高，建议提到 P1（纯数据配置，成本几小时）。
5. **导出前体积预览**：见 3.6，建议直接进 MVP 而非需求池。
